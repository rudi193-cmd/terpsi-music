## Top finds — the concrete transplant and its honest cost

### 1. Gordian Envelope — elision is the erasure primitive §5 is missing

§5 currently resolves erasure-inside-a-chain by **partitioning** (`consent/<subject_hash>`), which is correct but coarse: it deletes a subject's rows wholesale. Gordian Envelope adds the finer instrument. An envelope is a Merkle tree of SHA-256 digests over subject/predicate/object assertions; eliding any subtree replaces it with a marker **carrying the digest of what was removed**, so "digests for those parts … remain the same" and "signatures remain verifiable even for elided documents." Concretely: a guardianship record, a health note, or a piece of adjudication commentary can have one field cryptographically removed while the record's signature, and every chain link over it, still verifies — and the elision marker *is* a §16-shaped tombstone, in-band, dated by the enclosing assertion. Combine it with §5's partitioning, don't replace: partitions answer "delete this subject", elision answers "remove this field and prove nothing else changed."

**Honest cost, and it is not small.** (i) The GitHub license metadata on both `bc-envelope-rust` and `bc-envelope-cli-rust` resolves to `NOASSERTION`; Blockchain Commons' usual terms are BSD-2-Clause-Plus-Patent, but that has to be read off the actual `LICENSE` before a line is written — this is a §5 dependency, not a leaf. (ii) The format is dCBOR + URs; adopting it means adopting a serialisation the rest of the fleet does not speak, which by §16 rule 1 creates a pair and needs a named middle (envelope ↔ SQLite canonical store) in the same commit. (iii) Adoption footprint is small (the Rust lib has one fork and low single-digit stars) — this is a bet on a spec and a standards-body draft, not on an ecosystem. (iv) The `envelope` CLI is a genuine asset for the exit line: "your records are readable with one small open-source binary" is a better sentence than most. (v) If the risk is unacceptable, **SD-JWT is the same trick with more implementations** and a nearly-final IETF draft — salted digests in the signed payload, disclosures outside, "can be omitted without breaking the signature."

### 2. Clevis's `sss` pin — the escrow gap has a boring, packaged answer for half of itself

§5 says "there is no escrow" and proposes Shamir 2-of-3 across director / district admin / sealed offline share. `clevis` already ships this shape for LUKS: the **`sss` pin** "creates a key and divides it into a number of pieces. Each piece is encrypted using another pin (possibly even SSS recursively)" with a declared threshold `t`. So the mini-PC's disk can be bound to, say, 1-of-2 over {TPM2 on this hardware, a Tang server on the drop} for unattended reboot, while a separate escrow path covers total loss. GPL-3.0, Shell, actively pushed (2026-07-25), packaged in RHEL/Debian/Arch — exactly the "keeps working with nobody maintaining it" profile.

**Honest cost.** Clevis solves **disk** unlock, not `vault.key` and not per-record DEKs; §5's escrow gap is about the *key material*, and Clevis only gets you the volume. Tang is a service — it listens, which is fine on the band-room LAN with zero inbound from the internet, but it is a second box that has to exist and it must be inventoried in install acceptance (§10) or the drill will find it missing. TPM2 binding means the disk does **not** open on replacement hardware, which is the correct behaviour and simultaneously the exact failure mode §5 warns about ("the box's drive fails in October") — so TPM2-only is a trap; the threshold must always include a path that survives the motherboard. And `clevis` has a large open-issue count; treat it as infrastructure to configure and rehearse, not to read.

### 3. `tlog-checkpoint` + a witness — the anchor is already a standard, and #121's count is already in it

§5 requires "an anchor that distinguishes emptied from never-written" and #121 solved it by putting a `count` beside the hash. The C2SP `tlog-checkpoint` spec is that object, standardised: a signed note whose mandatory body is **three lines — origin, tree size, root hash** — where tree size is exactly the count, and where "a log must not sign any checkpoint which is inconsistent with any checkpoint it previously signed." Adopt the format verbatim for each `consent/<subject_hash>` partition head, the disclosure log, and §6's egress log, and three things follow for free: an existing verifier vocabulary, extension lines for the partition name, and — via `tlog-witness` — the ability to hand the checkpoint to a **witness** that stores only O(1) state and refuses to cosign anything not provably consistent with what it last saw. That is the piece §5's anchor cannot do alone: a local anchor plus a local chain can both be rewritten by whoever holds the box. A witness on §3's *drop* makes rollback of the anchor itself detectable, with no cloud and no inbound port (the log pushes to the witness).

**Honest cost.** You are adopting a spec, not a product: `transparency-dev/witness` (Apache-2.0, pushed 2026-07-27) is an HTTP service storing checkpoints in SQLite — small, but a service, on a second box, that someone must notice has stopped. Skew between "the checkpoint the box signed" and "the checkpoint the witness holds" is a §16 pair and needs its middle named. And per CLAUDE.md #18: a witness that nothing reconciles against is a **ledger**. The reconciliation — a scheduled compare that *fails loudly* — is the whole value; without it you have added a file.

### 4. keyfork — someone already built the escrow ceremony, in Rust, for exactly this threat model

Problem (b) asked for escrow across director / district admin / offline share, testable as an annual drill. keyfork is a Rust toolchain that does the mechanical part end to end on an air-gapped machine: generate a 256-bit seed, derive OpenPGP keys deterministically (BIP-32 over a BIP-39 mnemonic), provision smartcards, and **export a Shard file** in which the seed's entropy is Shamir-split with an M-of-N threshold and each shard is encrypted to a distinct Curve25519 OpenPGP key. The property that matters for a school: because the shards are *encrypted to individuals' keys*, a shard file can sit in the repo-adjacent operations directory or on a USB stick in the safe without being a usable secret — the compelled-copy tension §5 names ("every share is a copy that can be compelled or stolen") is reduced to "compel a share **and** the holder's smartcard." Derivation being deterministic also means the drill can *verify* recovery without exporting the recovered key: derive, compare public halves, destroy.

**Honest cost.** (i) I could not fetch `git.distrust.co` directly — the host 403s through this session's proxy — so language, licence split (binaries AGPL / libraries MIT), and the shard mechanism are **verified from indexed repository pages, not from a checkout**. Confirm before depending on it. (ii) v0.1.0 and one small vendor: this is closer to "read the design and reimplement the 200 lines you need over `bc-sskr`" than to a dependency you inherit. (iii) It assumes smartcards and an air-gapped machine — real cost, and correct cost, but it makes the drill a scheduled event with equipment, not a script in CI. (iv) AGPL on the binaries needs a decision if anything is shipped.

### 5. The wrapped-DEK header already exists twice — pick one and stop designing

Problem (a) asked whether there is a boring library for "one DEK per record, wrapped once per entitled circle, stored beside the ciphertext." There is, twice, and neither is a KMS.

- **age's format**: the header is a sequence of *recipient stanzas*, one per recipient, each wrapping the same file key; X25519 recipients; BSD-3-Clause; a tiny stable spec with independent implementations (`rage`) and plugin support (YubiKey, Secure Enclave). "Wrap the record DEK to `Family:1234`, `Staff:Ensemble7`, `Directors:Org1`" is three stanzas.
- **The AWS Encryption SDK message format**: a versioned, publicly specified header holding **N encrypted data keys** plus an authenticated encryption context, with **raw-AES and raw-RSA keyrings that touch no AWS service**. Apache-2.0 spec repo. Worth reading precisely because it is the mature version of the format §5 sketches — key commitment, algorithm-suite IDs, framed body — and because "encryption context" is where `subject_hash` and the L-rung belong.

**Honest cost, and one correction.** HPKE (`hpke-rs`, MPL-2.0, RFC 9180, all four modes) is the right primitive if the stack is Rust and you want the KEM/KDF/AEAD agility §5's diagram implies — but note MPL-2.0's file-level copyleft, and note that HPKE gives you a *primitive*, not a *format*: you would still be inventing the header, which is where the bugs live. Prefer adopting a format. Separately, a correction to a plausible-looking candidate: **gocryptfs (MIT, actively pushed 2026-07-22) does *not* fit** — its documented format derives content and filename keys from one master key via HKDF with per-file IDs used as nonces; there is no per-file DEK to wrap per circle. It is an excellent "documented at-rest format you can read without the app" reference for §11.1, and a wrong answer for §5's hierarchy. Do not let the README's shape substitute for the format doc. **Cryptomator** *does* use per-file keys wrapped by a masterkey with a published vault-format spec, but `docs.cryptomator.org` 403s through this proxy, so I am recording that as **unverified** rather than asserting it.

### 6. The drill is the deliverable, and three unrelated communities have already written it

§5's strongest sentence is "an untested key recovery is not escrow," and nothing in the fleet implements it. Three artifacts, from three unrelated fields, are all the same design:

- **ICANN's Root KSK ceremony**: a *script*, executed quarterly, in which tamper-evident bags are checked against recorded **serial numbers** on camera, Trusted Community Representatives each hold one card, every step is witnessed and countersigned, and participants give public testimony afterwards. Transplanted: the annual drill is a scripted, dated, two-witness event; the director and the district administrator are TCRs; the sealed offline share lives in a numbered tamper-evident bag whose serial is recorded in the previous drill's record. Cost: it is a calendar and a social obligation, and both decay when the director changes jobs — which is precisely the failure §5 is defending against, so the drill record must name a *role*, not a person.
- **Glacier Protocol**: proof that the deliverable can be a versioned public *document* with a **Withdrawal** phase — a rehearsal designed in from the start rather than bolted on — and that stating "~$600 of equipment, ~8 hours" up front is the honest form.
- **NDSA Levels of Digital Preservation**: a 0–4 ladder across five axes including **File Fixity and Data Integrity**, written for institutions with no dedicated staff, plus published guidance on when to check fixity. This is the pre-existing external rubric §10 wants for the durability half of §5 — and using someone else's published ladder avoids inventing a fourth ordinal scale after §15 already has three.

### 7. Crypto-shredding inside an append-only log: the precedents, and the bug to cite

Problem (c) has two shipping precedents worth reading and one worth quoting in a test name.

`axon-crypto-shredding-extension` (Java, small, updated 2026-01-19) does field-level crypto-shredding in an **event-sourced** store: fields carry `@EncryptedField`, a serializer wrapper encrypts them under a per-subject key held beside the log, and erasure deletes the key. The transplantable part is the *annotation-driven* boundary — the schema declares which fields are shreddable, so the classifier and the sealer cannot drift apart by hand. That is §16's "declaration-plus-enforcement" pair with the middle in the type system.

Hyperledger Fabric's private-data collections with `blockToLive` do the other half: purge the data, keep the hash on the immutable ledger, and verification still holds. Two things to take. First, the design confirms §5's resolution is standard practice, not novel. Second, and more useful: Fabric issue **#3844 — "No way to verify private data purge was completed successfully"** — no confirmation, no error detail. That is CLAUDE.md #18 and #19 in someone else's tracker: a purge whose completion cannot be observed is a **ledger**, and a shred with no test that attempts to read the shredded field and asserts failure **has not been shown to work**. Name a test after it.

Also note the legal caveat the practitioner literature raises against this whole family and which §5 does not currently record: under some readings of GDPR, encrypted personal data is still personal data, so crypto-shredding may not by itself discharge an erasure obligation. FERPA is a different statute with different mechanics, but the shape of the objection transfers, and the escrow design makes it sharper — **if a share can reconstruct the key, the shred is reversible by design.** The resolution has to be written down, not assumed: subject DEKs must be outside the escrow envelope, or the escrow must be documented as capable of undoing an erasure. That is an unresolved tension in §5 as written, and it is the single most consequential thing this scout found.

### 8. "Emptied is not absent" was solved in 2010, and again in archival science

Two oblique confirmations that #121's count-in-the-anchor is the standard answer, both usable as citations that this is settled rather than clever:

- **RFC 5848 (Signed Syslog Messages, 2010)**: Signature Blocks carry **First Message Number and Count**, and the RFC states that the authenticated log "implicitly indicates all gaps in the authenticated messages … because their message numbers are missing." Sixteen years old, Proposed Standard.
- **BagIt (RFC 8493)**: `Payload-Oxum` is `OctetCount.StreamCount` — total bytes **and** total file count — existing solely "for the purpose of quickly detecting incomplete bags before performing checksum validation," with an explicit warning that it is an optimisation and **MUST NOT** replace full checksum validation. Both halves transplant: put bytes-and-count in the export manifest (§11.1, W-6 graduate exports), and copy the warning verbatim — a cheap completeness check that gets treated as a validity check is exactly the `if existing and not verify(...)` bug #121 found.
- **DataCite's tombstone-page best practice** completes §16 rule 20 with a field list someone else already argued about: identifier, **date of deaccession, reason**, the governing policy, a statement that metadata is retained for the record, and **checksums of the removed files**. That last field is the one an invented template would omit, and it is what makes a tombstone verifiable rather than merely present.

## Weirdest things I found

**1. Surety's Digital Notary published its root hash as a New York Times classified ad, weekly, from 1995.** Haber and Stornetta's commercial timestamping service made its hash chain publicly verifiable by buying a small ad in the classifieds. Why the stretch is interesting: the hub has zero inbound ports, no cloud, and must survive the network being cut — which makes *external* anchoring look impossible. It isn't. **Print the season's final checkpoint (origin, count, root hash — 3 lines, ~80 characters) in the spring concert program, and mail it to the district office with the annual escrow-drill record.** Cost: a few square centimetres of a program nobody reads. Benefit: an adversary who truncates the chain must also recall several hundred printed programs held by families outside the institution, which is the strongest anchor property available to a band room and beats an online timestamping service on every host constraint. It also has a lovely secondary property — it makes the anchor legible to a person, which is §11.1's "readable without the application" applied to the integrity layer rather than the data.

**2. codex32: Shamir's Secret Sharing as a paper computer, with volvelles.** Blockstream Research shipped printable cardstock wheels and worksheets that let a human split and recombine a checksummed secret **with no computer at all** — "tedious and not for the faint-of-heart, but does not require any mathematical understanding; only perseverance, focus, and an ability to follow precise instructions." Why the stretch is interesting: §11.1's hardest criterion is "the box keeps working with the network cut and nobody maintaining it," and every software escrow tool fails it eventually — Rust toolchains rot, a 2026 binary may not run on a 2041 machine. A paper procedure does not rot. Even if codex32 is never used operationally, it sets the right *ambition* for the drill's fallback tier, and the volvelle is a genuinely delightful accessibility argument: the person who has to recover the key in fifteen years may not be technical, and "follow precise instructions" is a lower bar than "install Rust." Repo is dormant (last push 2024-06) and, importantly, **carries no license file** — verify before reproducing anything.

**3. SeedHammer: a machine that hammers key material into marine-grade stainless steel.** Air-gapped, stateless, no radios, dice-roll entropy, Raspberry Pi Zero, firmware under the **Unlicense**, actively pushed (2026-07-14) — and the physical output is a steel plate. Why the stretch is interesting: §5's "sealed offline share" is specified as a concept and will, in practice, become a USB stick in a drawer that is unreadable by the time it is needed. Bitcoin custody culture worked out a decade ago that the offline tier must be **a physical object that survives fire, flood, and format obsolescence**, and it built tooling for it. The transplant is not the machine (a school will not buy one); it is the *requirement*: the offline share must be recorded in a medium with no reader dependency — engraved, or stamped, or at minimum Bytewords on acid-free paper in a numbered tamper-evident bag. SSKR's Bytewords encoding exists precisely so that shares are transcribable onto metal by hand.

**4. Ephemerizer and Vanish — two elegant designs for cryptographic erasure, both disqualified, and the disqualification is the finding.** Perlman's Ephemerizer gives every file an expiration and deletes the ephemeral key at expiry — via a trusted external key service. Vanish (USENIX Security '09) Shamir-splits the key into a public BitTorrent DHT and lets node churn destroy the shares. Both are the *correct* abstraction for "erasure as key expiry" and both put the erasure guarantee in a third party the band room does not control — Perlman's own critics note the single-point-of-failure, and Vanish depends on a million-node public network that a school hub, by §6, cannot reach. Why the stretch is interesting: these are the two most cited academic answers to problem (c), and reading them makes the constraint precise rather than merely restrictive. **On a sovereign box, deletion of a key can only ever be as reliable as the box's own storage** — SSD wear-levelling, snapshots, backups, and the escrow shares all work against it. That argues for a specific and slightly unpleasant design commitment: subject DEKs must live somewhere with a *known* overwrite story (a separate small file per subject, fsync'd, on a filesystem you can reason about; ideally TPM-sealed, never in a rolling backup), and the erasure procedure must include destroying the backup generations that hold the key — which is a real operational cost §5 does not currently budget.

**5. Blockchain Commons' two-level group thresholds, and why "2-of-3" is the wrong ask.** SSKR supports a hierarchy: *n* of *m* **groups**, where each group itself needs *k* of *l* shares. Why the stretch is interesting: §5 proposes flat "2-of-3 or 3-of-5 across director, district administrator, sealed offline share," and flat thresholds encode the wrong politics. What an institution actually wants is something like *"one of {director, assistant director} **and** one of {district records officer, board secretary}, or alternatively the sealed offline share plus any one person"* — a structure that survives both a resignation and a single-institution capture, and that cannot be satisfied by two people from the same office. That structure is expressible as SSKR groups and is not expressible as a flat 2-of-3. It also gives the drill something to *test* other than arithmetic: the annual rehearsal should demonstrate that the **wrong** quorum fails (CLAUDE.md #19 — a guard that cannot be shown to fail has not been shown to work). Verify the license: `bc-sskr-rust` resolves to `NOASSERTION` in the API.

## Disqualified for hosted dependency (recorded per §11.1's "Delisted" discipline)

- **Any cloud-KMS envelope-encryption service** — the origin of §5's DEK/KEK pattern and the reason the pattern is well-documented, but §6's no-egress rule and §11.1's no-subscription rule both exclude it. Take the *format* (AWS Encryption SDK message header, above) and leave the service. This is the one case where the conceptually valuable thing is a hosted product: the header format is public, versioned, Apache-2.0, and works offline with raw keyrings, so nothing is lost.
- **Perlman's Ephemerizer** (external key-expiry service) and **Vanish** (public DHT) — see Weirdest #4.
- **Tang** — worth flagging as a *near* miss rather than a disqualification: it is a self-hosted network service, so it satisfies "no cloud," but it means a second box that listens on the LAN and must be present at boot. Acceptable, and it must appear in install acceptance (§10) and in the drill, or the first power cut after the drill is when you find out it is gone.
- I found **no hosted escrow or social-recovery product** worth naming here; the commercial custody offerings in this space are subscriptions and I did not verify any well enough to describe.

## Two gaps nothing I found covers

1. **Escrow versus erasure is an unresolved contradiction in §5, not a tension to note.** If a 2-of-3 quorum can reconstruct the root key, and subject DEKs are reachable from the root key, then every crypto-shred is reversible by a quorum — and the guardian was told the record was destroyed. Either subject DEKs sit outside the escrow envelope (and are therefore genuinely unrecoverable, which is a different promise to make to a FERPA inspector), or the escrow is documented as capable of undoing erasure. Nothing found makes this choice for you. It is a §12 "decision to lock now."
2. **Nothing in this slice ships an escrow *drill harness*.** ICANN has a ceremony script, Glacier has a withdrawal phase, keyfork has a wizard — none of them is a test you can run in CI that proves the current shares still reconstruct the current key. That is a small piece of original work (derive, compare public halves, assert the wrong quorum fails, write a dated drill record), and by CLAUDE.md #19 it is the part that turns §5's escrow paragraph from a plan into a guarantee.
