## Top finds, with the transplant and its cost

### 1. Part-DB — the cabinet/drawer problem is already solved, in the wrong domain

Verified from source, not from marketing: `src/Entity/Parts/PartLot.php` defines a `PartLot` bound to a `StorageLocation` with an `amount`, and `PartLotSelectType.php` renders a lot as `getStorageLocation()->getFullPath()` — i.e. locations are a **hierarchy with a materialised path**, and stock is held by *lot at a location*, not by a scalar column on the item. Two boolean flags on the lot are the reason this is the top pick rather than a merely adequate one: **`instock_unknown`** and **`needs_refill`**. That is `CLAUDE.md` #13 pre-built — a lot whose count was never audited reads `unknown`, not `0`, and the system can distinguish "we have zero 2nd clarinet parts" from "nobody has ever counted the 2nd clarinet parts." A library built on a `copies_on_hand INTEGER DEFAULT 0` column cannot express that, and will silently report a drawer nobody has opened as empty.

**Transplant.** Take the schema, not the app: `Work → Part (2nd clarinet) → PartLot(location, amount, amount_unknown, needs_reprint)`, with `StorageLocation` as a self-referencing tree whose full path is `Cabinet 3 / Drawer B / Folder 12`. Part-DB's barcode/label generator covers *storage locations as well as parts*, which is what makes an annual drawer audit tractable.
**Cost.** Adopting the running app means AGPL-3.0 plus a Symfony/PHP + Node-for-assets build, and its vocabulary is stubbornly electronic (manufacturers, footprints, datasheets) — a director would be reading "part" in a second sense all day, and §4's own noun list ("Library") argues against shipping someone else's domain words. Reimplementing the four tables is a few days and carries no licence obligation. Recommend: read the entities, write our own.

### 2. OpenLP's song-usage plugin — performance-rights reporting, already built once

This is the find I would not have predicted, and it is the closest working analogue to §4's ASCAP/BMI line. `openlp/plugins/songusage/songusageplugin.py` states "This plugin tracks the usage of songs in services," and the recorded fields are, verbatim from source: `usagedate`, `usagetime`, `title`, `copyright`, `ccl_number`, `authors`, `plugin_name`, and `source` — where `source` distinguishes **"display" from "printed"**. Churches face the same structural problem as school programs: a blanket licence (CCLI there, ASCAP/BMI/SESAC here) whose renewal requires a defensible log of what was actually performed or reproduced, assembled from memory after the fact by a volunteer.

**Transplant.** Two things. First, the *field set* — a usage row keyed to a datetime, the work, and the rights holder, with a mode discriminator. Ours needs more modes than two: `performed`, `printed_in_program`, `copied_for_folder`, `posted_publicly`, `streamed`. Second, and more valuable, the *provenance*: OpenLP does not ask anyone to fill in a usage form. Rows are emitted as a side effect of a song being displayed. The equivalent here is that a performance-rights row is written when a piece appears on a sealed concert programme or set list, never typed in by a director in June. That distinction is exactly `CLAUDE.md` #18 — a usage log fed by a human's memory is a ledger; one emitted by the act of programming is closer to enforcement.
**Cost.** Nothing to adopt in code (GPL, PyQt desktop app; the licence is stated by the project but was not confirmed by the fetches, which only read the plugin source). The transplant is a table, a writer hooked into the programme/set-list seal, and an export. Days, not weeks. The hard part is not the code — it is deciding that `posted_publicly` is a usage class, because that is the one that produces takedowns (§20, "copyright takedown of a posted performance video").

### 3. ODRL — the rights-expression language for "custom arrangement permissions"

§22 calls copyright-as-first-class-data differentiating. The risk is that "first-class" degrades into a `rights_status` enum plus a notes field, which is a ledger. ODRL is the W3C rights-expression language, and — verified from `KNowledgeOnWebScale/ODRL-Landscape` — there is a real tooling ecosystem: `SolidLabResearch/ODRL-Evaluator` (MIT, TypeScript) takes a policy, a request, and a *state of the world* and emits a **Compliance Report** saying which rules are active and whether their constraints hold, validating input against SHACL shapes first; `SEAMWARE/odrl-pap` (Apache-2.0, Java/Quarkus) compiles ODRL into Rego for Open Policy Agent; plus ODRE (Java/Python), Prometheus-X's Node evaluator, and Polival (Rust). Several independent implementations of the same vocabulary is the signal that matters — it means the model has been pushed on.

**Transplant.** A marching-show arrangement permission is genuinely a policy, not a status: *the arranger permits `arrange` and `perform` of this work, by this ensemble, for this season, at up to N competitive performances, excluding broadcast, conditional on a purchased copy per performer.* That is an ODRL `Agreement` with an `assignee`, dated and counted `Constraint`s, and a `Duty`. Encoding it that way buys three things a status enum cannot: the permission expires by its own terms (§4's rental return dates, §7.4 I-6's declared timebound), the count constraint is checkable against the performance log from find #2, and the per-performer-copy duty is checkable against the part counts from find #1. Store the policy as JSON-LD alongside the catalogue row — readable without the app, per the hard constraints.
**Cost.** Do **not** adopt odrl-pap: it wants Postgres + OPA + an API gateway (APISIX/Kong/Envoy tested), which is a fleet on its own and violates the modest-box rule. The ODRL-Evaluator is the right size but is research software, and the fetch could not confirm which constraint operand types are implemented (`ODRL-Support.md` in-repo documents this — read it before committing). Realistic plan: adopt the *vocabulary and JSON-LD shape* now, hand-write the three or four constraint checks we actually need (date window, performance count, ensemble identity, publication channel), and keep the evaluator as a conformance oracle in tests rather than a runtime dependency. That also satisfies #19 — a rights guard that cannot be shown to refuse has not been shown to work, and ODRL's own test suite gives us forbidden acts to attempt.

### 4. MEI — "the same work in three arrangements", verified in the schema's own examples

Fetched from `music-encoding/music-encoding`: `source/examples/FRBR/FRBR-sample080.txt` and `-081.txt` contain `<expression>` elements carrying `<title>Version for piano</title>` and a `<perfMedium><perfResList>`, and `source/examples/header/header-sample059.txt` is a `perfResList` explicitly commented `<!-- concert band -->`. So the schema ships a worked FRBR example of one work with multiple expressions distinguished by arrangement and by medium of performance — and a concert-band instrumentation example — which is precisely §4's "same work in three arrangements" plus the instrumentation field, from a standard maintained by music librarians rather than invented here.

**Transplant.** Adopt the *layering*, not the XML: `Work` (Holst, First Suite in E♭) → `Arrangement` (full band / Boosey; young-band reduction; brass-choir transcription) → `Holding` (the physical set in Drawer B) → `Part` (2nd clarinet ×8). Rights attach at the Arrangement level, not the Work — which is the whole liability point, since the Work may be public domain while the 2004 arrangement is emphatically not. Instrumentation belongs on the Arrangement as a *resource list with counts*, not a free-text "instrumentation" string, because that is what makes instrumentation gap analysis a set-difference instead of a regex.
**Cost.** Low, if used as a conceptual model and a target for interchange. High if we try to *store* MEI — it is a large XML schema and nobody in a band room will hand-edit it. Verovio (LGPL/GPL, C++ with Python wheels and a CLI) renders MEI and MusicXML to SVG offline and is the natural companion when a digital part actually has to be drawn.

### 5. Arctos and Darwin Core — the specimen world already solved part-level inventory and missing-part tracking

Two verified pieces from the natural-history vein, which is where this brief's "go weird" instruction paid off best.

**Arctos** (`ArctosDB/arctos-archive`, `v6.x/ContDet.cfm`) joins `cataloged_item` → `specimen_part` (via `specimen_part.derived_from_cat_item`) → `coll_obj_cont_hist` → `container`. Read that as: one catalogued *thing* has many physical *parts*, each part's location is a **container-history table rather than a location column**, and containers nest. A mammal skin, its skull, and three tissue vials live in three different freezers and get loaned separately — structurally identical to a score whose conductor's copy is on the podium, whose 1st trumpet is in a student's folder, and whose 2nd clarinet ×8 are in Drawer B. The history table is the part worth copying: "where is this part" and "where has this part been" are the same query, which is what a lost-music fee dispute actually needs (and #3/#7: you end a placement by dating it, not by overwriting a column).

**Darwin Core** supplies the vocabulary. Verified from `tdwg/rs.tdwg.org` term CSVs: `disposition` is defined as "The current disposition of the cataloged item," with examples **"in collection", "missing", "voucher elsewhere", "duplicates elsewhere"**; `individualCount` is "The number of individuals present in the lot or container." (The rows quoted are from the 2007 `dwc/curatorial/` namespace, marked deprecated, superseded by the 2009 `dwc/terms/` versions — the terms live on, the URIs moved.) "Voucher elsewhere" and "duplicates elsewhere" are exactly the states a band library needs and that no home-grown enum ever includes on the first pass: *this part is not lost, it is in the middle-school library*; *we hold three copies beyond the set*.
**Cost.** Zero adoption cost — this is a schema idea plus four vocabulary values, and per `CLAUDE.md` #14 they want a prefixed mapping table (`D-in-collection`, `D-missing`, `D-elsewhere`), not bare strings and not colour. Arctos itself is not adoptable: the fetch could not confirm a licence, the code is ColdFusion against Oracle, and it is a hosted consortium service. Read the schema, take the two joins, leave the app.

### 6. The watermarking plan needs to be honest about what watermarks do

`pdfcpu` (Apache-2.0, Go, single static binary, 8.7k★) has first-class `stamp` and `watermark` commands, which makes per-student PDF distribution a trivial shell-out with no runtime to install — the right choice over Stirling-PDF, which is a JVM service under an "open-core" grant that is not a clean OSS licence. For the forensic layer, `invisible-watermark` (MIT) implements dwtDct/dwtDctSvd/RivaGAN at 32–64 bits, **but its own README states the algorithms fail under resizing, rotation, aspect-ratio change and cropping, and that "all algorithms do not perform well for web page screenshots."** That is decisive: the realistic leak path for a student part is a phone photo or a screenshot, which is precisely the attack these algorithms lose to. So the design should be a **visible, per-student, per-issue stamp** (name, date, licence reference, "copy 4 of 8") applied with pdfcpu — visible marks deter and are legible in a photo — plus a recorded issue ledger, and an invisible payload only as a defence-in-depth afterthought that is never described to anyone as tamper-proof. `audiowmark` (GPL-3.0, 128-bit, survives 128 kbit/s MP3/OGG) is the equivalent for reference recordings, which is a different §1 problem.

### 7. Rights vocabulary and the four-year rotation, briefly

`rightsstatements/data-model` publishes standardised rights statements as **SKOS in Turtle plus per-language JSON-LD**, CC0. Adopt the URIs rather than inventing a `rights_status` enum: they are the GLAM world's settled answer to "in copyright / no copyright / status unknown", and — critically for `CLAUDE.md` #13 — *undetermined* is a first-class value in that vocabulary rather than an absence. The statement list itself could not be enumerated (host blocked); read `rights-statements.ttl` from the repo before wiring it up.

For **four-year rotation**, no domain tool exists and none is needed: `google/or-tools` (Apache-2.0, CP-SAT, pip, fully offline) is the right hammer. The problem is a constrained assignment — for each concert cycle choose repertoire covering required styles/grades, such that no student's four-year window repeats a work, subject to instrumentation feasibility and measured difficulty. Instrumentation feasibility is a set-difference against the Arrangement's resource list plus cross-cue substitutions; that is a *filter feeding* the solver, not part of it. Note `CLAUDE.md` #6 sharply here: the solver may rank *pieces*, never students. Chair placement and limited slots must stay out of this model entirely, and the rotation solver must not be reachable from a code path that scores a person.

## Weirdest things I found

1. **Arctos's `specimen_part` + `coll_obj_cont_hist`.** A museum system for skulls and tissue vials contains the cleanest part-level inventory model I found for sheet music: one catalogued item, many parts, and location as a dated container history rather than a column. Herbarium/vertebrate collections have been dealing with "the set is incomplete and pieces are on loan to three institutions" since the nineteenth century.
2. **Darwin Core's `disposition` value "voucher elsewhere".** A biodiversity vocabulary contains the exact state a band library needs and always forgets: the part is not lost, it is legitimately somewhere else. Also "duplicates elsewhere" for the copies beyond the set.
3. **OpenLP's song-usage plugin.** Church presentation software has a shipped, working implementation of blanket-licence usage reporting, including the display-versus-printed distinction, generated as a side effect of performing rather than typed into a form. School music programs carry the same liability and have no such tool.
4. **`SEAMWARE/odrl-pap`: compiling rights into Rego.** Someone built a pipeline that turns a rights policy into Open Policy Agent rules enforced at an API gateway. Wildly over-engineered for a band room, and it is the proof that "copyright as first-class data" can mean *evaluated at the point of access* rather than *typed into a field*.
5. **Part-DB's `instock_unknown` flag.** An electronics inventory app for hobbyists independently arrived at `CLAUDE.md` #13: an uncounted drawer must not report zero. Also worth noting for contrast: **Muscat, RISM's own music-source cataloguing application, ships no LICENSE file and no licence statement in its README** — the most domain-relevant cataloguing app found is legally unusable as code, which is its own small lesson about what "open" means in the musicology stack.

## Gaps — things the brief asked for that appear not to exist

- **No maintained open-source public-domain / copyright-term calculator.** A GitHub search for public-domain/copyright calculators returned a single trivial repo (`nehemiaharchives/copyrightcalc`, 0★, HTML). The European `outofcopyright.eu` calculator could not be reached (host blocked) and its code was not located. Determination logic will have to be written and cited from a named authority — and per §12's lesson about uncited thresholds, that authority needs a URL and an observed date, not a remembered rule.
- **No open-source rights-clearance or cue-sheet workflow tool.** Searches for cue-sheet/rights-clearance repos returned nothing. The documentary-film clearance workflow exists as practice, not as software. What is transplantable is its *artifact*: a per-use clearance record with term, territory, media, and an expiry — which is what ODRL encodes.
- **No open-source orchestral/band library part-management application.** Searching sheet-music repos surfaces OMR, renderers, and downloaders; the only management app found (`Airsequel-Sheet-Music`) depends on a hosted service. The professional-orchestra librarian world (MOLA) runs on commercial tools. §4 is genuinely unserved — which is the strongest argument in this report for building it.
- **No open dataset for difficulty calibration.** Grade levels (state lists, publisher grades) are proprietary or informal. Calibrating charts against measured ensemble ability will need our own data and should be labelled a `P4`/`P5` estimate, not a grade.
- **Score-markings-to-parts is a lonely vein.** MELD (Web Annotation anchored into MEI) is the right idea and the repos are quiet (last touched 2025-08, single-digit stars). MuseScore does linked parts natively but the fetch could not confirm its part-linking or batch-export behaviour from the README. Expect to build the anchor model ourselves on Verovio element IDs.

## Unverified — do not quote forward without checking (§18 item 0 discipline)

Blocked hosts prevented verification of all of the following. Each is a claim to check, not a fact:
- **MARC 382 (Medium of performance) and 048 (number of instruments/voices)** subfield structure, including per-instrument counts — `loc.gov` unreachable. This is the single most promising unverified item: if 382 `$n`/`$s` carry performer counts as claimed, it is a standard encoding of "two bassoons, no oboe."
- **LCMPT** (LC Medium of Performance Thesaurus) existence as downloadable SKOS — `id.loc.gov` unreachable. Would be the authority file for instrumentation terms.
- **The ODRL Information Model** entity and constraint inventory, and its Recommendation status/date — `w3.org` unreachable. Everything above about ODRL rests on the tooling repos, which are real, not on the spec text.
- **The rightsstatements.org statement list** and categories — repo confirms SKOS/Turtle/JSON-LD and CC0; the enumeration was not read.
- **PREMIS rights bases** (copyright/licence/statute/donor agreement) as implemented in Archivematica — `archivematica.org` unreachable. Worth a second look: PREMIS rights is the other serious candidate model for rights-as-data, alongside ODRL, and pairs with #11 (sidecars promoted by a human).
- **MusicBrainz** work-to-work "arrangement of" relationships and ISWC handling — schema docs not reachable; only the repo's stack (GPLv2+, Perl, Postgres 18+, Node 24+) was confirmed.
- **Specify 7's Preparation model**, **MTGJSON's per-format legality fields**, **fontbakery's specific licence-metadata checks**, **Audiveris headless/batch operation**, **CantusDB's licence name**, and **Arctos's licence** — all unconfirmed by the fetches that were possible.
