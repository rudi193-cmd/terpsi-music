# Scout 03 — the drop (untrusted relay) and the local-first encrypted edge replica

Slice: §2 Zone B (the drop) and Zone C (edge devices), against the criteria in §3, §4.2 option (b), and §4.3's `jeles-remote` bar. Constraints carried in: one lane per student sealed against siblings (§7.4 W-1/W-3), no group grants (W-2), metadata is the disclosure that matters (§4.2 / `corpus-lens`), no revocation by deletion (§7.1), and the §11.1 exit-plan test for anything we depend on.

### The naming trap, and a second-order version of it

The open-source **Willow Protocol** (`earthstar-project`, `willowprotocol.org`) is unrelated to the fleet's internal Willow. It is a genuinely strong candidate on its merits and is ranked #3 below.

But there is an operational hazard beyond confusion in prose: adopting it puts `willow-rs` / `willow-js` / `meadowcap` into the dependency manifest **next to** internal `willow-mcp`, `willow-gate`, `willow-data-vault`, `willow-config`, `willow-2.0`, `willow-seed`. Every future grep for "willow" in this repo returns both fleets. Given that §16's whole subject is declaration/enforcement pairs going unnoticed, importing a name collision into the manifest is a real cost, not a cosmetic one. If Willow is adopted, vendor it behind a domain-noun facade (`entitlement/`, per the plain-domain-nouns rule) and record the collision in `FLEET_SEAMS.md` on the way in.

## Top finds, with the transplant and its cost

### 1. briar-mailbox — the drop already exists as a working artifact

Briar Mailbox is the closest thing in open source to §3's paragraph. Its job list is our job list: authenticate a connection as belonging to an owner, accept ciphertext left by a contact, hold it, hand it over, delete it. It ships three ways (Android app, fat JAR for x86_64 Linux, Docker), which is the same deployment surface a band-room hub plus a small VPS needs.

**Transplant.** Take the shape and the auth model, not the code. Specifically: an owner-scoped connection where the credential *is* the mailbox binding, so there is no session in which "which mailbox?" is a parameter the client supplies — which is the un-passable-parameter discipline of §6 applied to the relay's own API, and is what makes "cannot enumerate one mailbox from another's session" structural rather than checked. Pair it with §4.3's observation that Grove's u2u already supplies signed identity, verified origin, and per-contact consent flags defaulting to `False`: Briar Mailbox is the missing confidentiality-and-holding half.

**Cost.** AGPL-3.0-or-later and Java. AGPL on a network service is a licensing decision the org has to make deliberately, and the JVM is not the runtime the rest of this fleet uses. It is also tightly coupled to Briar's transport and contact model, so "vendor it" would create exactly the §16 pair (vendored copy with no named reconciler) this project exists to avoid. Read it, write ours, cite it in the design doc as prior art. Roughly a week of reading and a fortnight of writing for the relay itself.

### 2. SecureDrop Protocol's message-fetching — turn "cannot enumerate" into a theorem

This is the single most valuable idea I found for the relay. In v0.4 (spec read directly from `docs/protocol.md` in this session), fetching works like this: the client sends `RequestMessages`; the server iterates `k ∈ [0, MAX_MESSAGES]`, and for each ciphertext in its store computes a blinded challenge from that message's group elements, **padding out to `MAX_MESSAGES` with freshly random group elements and random IDs where it has no message**; it returns the whole set of challenges. The client derives a key per challenge from its own fetch secret and trial-decrypts; the ones that open are its message IDs, which it then requests individually.

The properties that matter here: the server does not know which mailbox the fetcher owns, the response size is constant regardless of how many messages a given mailbox has, and there is no per-mailbox index for the relay to hold or leak. Compromise of the relay yields even less than §4.2's "which mailboxes talked, when, roughly how much" — and §4.2's own `corpus-lens` paragraph is the argument for wanting that: *timing alone reconstructs a custody arrangement.* A guardian mailbox that receives traffic on alternating weekends is the disclosure this system is built to prevent, and content sealing does not help.

**Transplant.** Adopt the *pattern* at a coarser grain than the paper's: a fixed-cardinality challenge set per collection round, per padding bucket, on a fixed flush schedule. You do not need the PQ/hybrid key schedule (X-Wing, ML-KEM-768, SD-APKE/SD-PKE) that the SecureDrop threat model demands. You need the constant-size padded challenge set and the "receiver reconstructs `info` locally, it is never transmitted" discipline.

**Cost.** Real. It is `O(MAX_MESSAGES)` group operations per collection round, which sizes the relay to the *store*, not to the traffic — for hundreds of families and a 5% transactional share that is affordable, and it is why the SMS split in §4.1 makes this tractable at all. And the README is unambiguous: proof-of-concept, protocol not finalized. Implement the idea, do not depend on the code. Also record honestly what it does *not* hide, `corpus-lens`-style, with a test that asserts the surviving leak — a limit you have measured and disclosed is a different artifact from one you have not looked for.

### 3. Willow Protocol + Meadowcap — the entitlement model, and the W-2 problem solved on paper

Willow's data model addresses entries by (namespace, subspace, path). Meadowcap issues read or write capability over a three-dimensional *area* of that space, and those capabilities can be delegated and **further restricted** by the holder; it can also grant the ability to grant, which is what makes it work offline. This is the shape §7.4 W-2 demands: a capability names a subspace, so `Student:1234` is expressible and `"the drumline"` is not — a wildcard is not a thing you can accidentally say if your grant primitive is an area anchored at a named subspace.

**Transplant.** Steal the *area* algebra and the restriction-only delegation rule as the wire format for grants, and make "grant issuance validates against Schedule A prohibited scopes before minting" the enforcement point (§14 names `envelopes/pre-approved.json` as that surface). One lane = one subspace, and sibling sealing is then the absence of a capability rather than a filter that could be forgotten.

**Cost, and a caution.** `willow-rs` **was archived on GitHub on 2025-10-23** and relocated to Codeberg, which this session could not reach (403). That is precisely the §14/§18-item-0 situation: I can confirm the move, I cannot confirm the destination is alive. Before this becomes a dependency rather than an influence, someone must open `codeberg.org/worm-blossom/willow_rs` and check commit recency and whether WGPS (the sync protocol) is implemented — the archived GitHub README said the sync protocol was "eventually" and not yet present, and a capability system without a sync protocol is half the job. Also the name-collision cost noted above. Verdict: adopt the model now, adopt code only after that check.

### 4. Peergos's cryptree — sealed sibling lanes as cryptography, not as a WHERE clause

Peergos implements the cryptree scheme (from Wuala) and extends it to hide "file size, names, thumbnails, directory structure and more"; storage chunks carry random labels with no cross-links visible to the server, so the server cannot even deduce a file's size. Sharing is done by handing over a capability to a subtree; links carry key material after a `#` so it is never sent to the server.

Why this matters more than it looks: W-3 says lanes are mutually sealed by default and *"a shared event is two lane entries with one referent."* §7.3 already names `quiet-corner` as the known-bad precedent — a sensitivity vocabulary declared per field and enforced nowhere. A cryptree makes sibling sealing *unforgeable*: lane B's entries are not merely filtered out of the parent's query, they are keyed under material the parent's capability cannot derive. That converts §16's declaration/enforcement pair into a single artifact — the guarantee and its enforcement are the same object.

**Transplant.** The subtree-capability structure and the metadata-hiding measures (random chunk labels, no cross-links, size hidden by padding). Applied here: the per-subject partitioning §5 already adopted from `marching-arts` #115 (`consent/<subject_hash>`) becomes a keyed cryptree per lane, and the "unscoped read or write fails closed" rule becomes "an unscoped read has no key," which cannot be bypassed by a caller who forgot the scope.

**Cost.** AGPL-3.0 and Java, and the storage layer is IPFS-shaped. Do not adopt. The cryptree construction is well documented and small enough to reimplement over §5's existing HPKE-wrapped-DEK hierarchy; the honest estimate is that the *key-derivation design* is a few days and the *test suite that proves a sibling capability cannot derive the neighbour's key* is longer — and per CLAUDE.md #19 that mutation test is the deliverable, not the code.

### 5. CHT Core — the only candidate that proves this shape survives contact with reality

Everything above is a protocol. CHT Core is a deployed system: AGPL-3.0, 552 stars, 12,472 commits, a Digital Public Good badge, offline-first health apps for community health workers on bad networks, with **per-user partial replication** — the `medic` database replicates only a subset to each user, plus a per-user `medic-user-{username}-meta` database. Health data, hierarchical roles, SMS integration, PouchDB on the device. That is a startlingly close structural match to a music program: hierarchy, per-worker slice, health content, SMS as the mass channel, no signal in the field.

**Transplant.** Two specific things. First, the **per-user database** rather than the per-user *filter* — filtered replication is the well-known CouchDB performance cliff, and CHT's answer of a separate DB per user is the same answer W-1 demands for a different reason (separate storage, permissions, audit trail from the first write). The privacy rule and the performance rule point the same way, which is worth stating in the design doc because it means the expensive-looking option is the cheap one. Second, read their conflict-resolution and their documented partial-replication limits before designing the write queue.

**Cost.** Do not adopt the platform — it is a large AGPL JS/CouchDB monolith with a domain model that is not ours, and adopting it would make the canonical store CouchDB, colliding with §5's "canonical store is read-only to the app." Also: their server reads plaintext, so it is a Zone A architecture, not a Zone B one. This is a read-and-learn, at maybe two days of reading for a design decision that would otherwise be discovered the hard way in season two.

## Weirdest things I found

1. **A relay that answers every fetch with a constant-size set of decoys.** SecureDrop Protocol's server pads its challenge set to `MAX_MESSAGES` with random group elements, so a mailbox with one message and a mailbox with none produce byte-identical responses. It is the mirror image of the usual instinct — instead of hardening an index, delete the index and make the client search. This is the answer to §4.2's custody-schedule-from-timing problem, and I would not have found it looking for sync libraries.

2. **NNCP: UUCP's descendant, and it ships dead drops as a feature.** Store-and-forward spool utilities where relayed packets get *onion* encryption so intermediate nodes see nothing, and whose own feature list names "offline sneakernet/floppynet, dead drops, sequential and append-only CD-ROM/tape storages, air-gapped computers." A design where the transport can be a USB stick carried on a bus is not a curiosity for this app — it is §11.1's exit plan and the stadium-with-no-signal case in one artifact. Append-only tape as a supported medium is also a rather pointed answer to "never revoke by deleting."

3. **Serval's MeshMS stores a conversation as two one-way journals, one per direction.** Not one shared log with two writers — a pair of bundles. Serval reached that from mesh constraints (no coordination, no shared mutable state); §7.4 W-3 reaches the same structure from guardianship doctrine (*"a shared event is two lane entries with one referent"*). When a networking project and a wardship charter converge on the same schema, that schema is probably right, and it is a much better citation for the design doc than an assertion that no precedent exists.

4. **Talek: read-only capabilities over PIR "topic handles."** A messaging system where the untrusted server cannot tell which topic you read, and where sharing read access *is* handing over a handle. That is §7's authorization model and §4.2's metadata problem addressed by the same primitive. It is research code (52 stars, Go, MIT) and the cost is high, but it establishes that "the relay learns which mailboxes talked" is a *choice*, not a floor — which changes how §4.2's compromise paragraph should be written.

5. **The IETF already standardized the drop, and it is in every phone.** Web Push (RFC 8030 + RFC 8291) is an untrusted relay that holds opaque, size-capped, TTL-bounded blobs addressed to opaque endpoint URLs, cannot read payloads, has no domain schema, and is strictly push — the client never listens. `mozilla-services/autopush-rs` (MPL-2.0, Rust, 332★, 942 commits) is a readable implementation. For the *notification* channel of a PWA this is a drop we do not have to build, and it composes with §4.1's SMS split rather than competing with it.

*Honourable mention:* the amateur-radio path. `la5nta/pat` (Go, 591★) speaks Winlink store-and-forward over AX.25/PACTOR/ARDOP, and Reticulum runs the same store-and-forward semantics over LoRa at a 500-byte MTU with no source addresses on packets. A bus in a parking lot with no cell signal is, from a protocol standpoint, a solved problem from 1985 — and the solved version assumes the relay is hostile.

## What fails, and precisely why

**Failing "sync only my slice":**

- **Automerge (MIT, 6.5k★) and Yjs, used plainly.** The unit of synchronisation is the document; there is no partial or subset sync *within* a document, and the docs do not offer one. So a parent's replica must receive whole documents. If a lane is a document you have satisfied W-1 by accident and still leak the document graph to the relay; if a roster is a document you have violated W-3 outright — *"a rehearsal attended by 150 students is 150 entries against one `Rehearsal`, not one row with a roster column."* The best evidence that this is a real gap and not my reading of it: Ink & Switch built Keyhive/Beelay specifically to add capability-scoped, server-unreadable sync on top of Automerge. Use Automerge for merge semantics inside a lane; never as the sync boundary. Full-history CRDT also collides head-on with §5's hash-chain erasure finding.
- **CouchDB/PouchDB filtered replication, bare.** The server reads plaintext (Zone A architecture wearing Zone B clothes), the browser store is unencrypted IndexedDB by default, and filtered replication is the documented scaling cliff. Note what CHT actually did: **database per user**, not a filter. If you take PouchDB, take that lesson with it.
- **ElectricSQL (Apache-2.0, 10.3k★).** Shapes are genuine partial replication and the license is clean, but it is a *read-path* sync engine — no write queue — the sync service reads Postgres plaintext, and shape authorization is app-supplied at the edge. That is a fine Zone A read-scaler and a disqualified Zone B relay. It also gives you a queryable HTTP endpoint, i.e. §4.2 option (a).
- **Rocicorp Zero (`rocicorp/mono`, Apache-2.0 — license read directly).** Query-driven partial sync with a permissions layer, which is the right *ergonomics*. But `zero-cache` holds plaintext and is a queryable service. Same verdict: option (a), not (b).
- **Solid / CommunitySolidServer (MIT, 600★).** The pod server stores and reads plaintext; access control (WAC/ACP) is server-enforced. That is a gate on trusted infrastructure — a Zone A pattern. Useful as a personal-data-store *shape* (the user chooses the server, §11.1 likes that) and useless as the drop. Same for `remotestorage.js` unless the app encrypts above it.
- **Public-repository personal-data-store designs in the AT Protocol family** are excluded by design — repositories are world-readable. Not verified in this session; excluded on published-design grounds, and I am not going to research it further for a system holding minors' medical forms.
- **Matrix homeservers** (design-level exclusion, not verified in session): E2EE plus a relay looks close, but a homeserver holds room state, membership, and an admin API. That fails "no schema of the domain, no admin UI, no user table beyond opaque IDs" three times over.

**Failing on license or sovereignty:**

- **PowerSync (`powersync-ja/powersync-service`).** Its sync rules are the best-fitting *semantics* I found — parameter queries on `user_id` from the JWT yielding one bucket per user, plus a persistent FIFO upload queue that survives restarts, which is §3's "writes queue and flush when connectivity allows" exactly. But the license, read directly from the repo, is **FSL-1.1-ALv2** — Functional Source License, converting to Apache-2.0 only after a delay. That is not OSI open source today. Against §11.1's exit-plan requirement and the `awesome-sovereign-software` five-point test, a dependency you cannot fork *now* is a different class of risk than one you can. And the service reads plaintext anyway, so it would be a Zone A component deployed into Zone B. **Steal the bucket-and-queue semantics; do not take the dependency.**
- **Reticulum's reference implementation** is under a custom "Reticulum License" (the protocol itself is public domain). Custom licenses need legal review before they go anywhere near a district-adjacent deployment. LXMF is MIT; the stack under it is not straightforwardly so.
- **libSQL (MIT, 17.0k★)** — the README itself points new development at Turso, a separate product, and notes libSQL keeps SQLite's single-writer model while the bidirectional-offline-sync capability belongs to Turso. Confirm exactly which artifact is MIT before treating database-per-lane as a solved substrate.
- **`pubkey/rxdb` (Apache-2.0 core, 23.3k★)** has a premium plugin tier. I could not determine in this session which encryption plugin is free and which is paid. Flag before adopting; do not assume the encrypted-store path is Apache-2.0.

**Failing on maturity — good ideas, not yet dependencies:**

- **Keyhive/Beelay**: README says "DO NOT use this release in production" and "not been through a security audit." It is nonetheless the closest thing to what this slice wants, and worth tracking deliberately.
- **p2panda**: "APIs are not yet considered stable for production use."
- **Jazz**: "Jazz 2.0 alpha with an entirely new API."
- **Syncthing untrusted devices**: its own documentation says "should still be considered beta / testing only," and slicing is folder-granular — one folder per lane means hundreds of folders and no per-record capability.
- **SecureDrop Protocol**: PoC, protocol not finalized.
- **Tahoe-LAFS**: mature, but no mobile/PWA client, no offline write queue, and an erasure-coded grid is far heavier than a mailbox. Take the capability vocabulary, not the system.

## What I would actually build, given the above

**The drop** = `magic-wormhole-mailbox-server`'s shape (nameplate/mailbox vocabulary, WebSocket, tiny SQLite spool) + `briar-mailbox`'s owner-bound-credential auth so "which mailbox" is never a client-supplied parameter + SecureDrop Protocol's padded constant-size challenge set for collection + `chatmail`'s operational policy (refuse anything not sealed, auto-delete on a fixed schedule, collect no metadata, scrub and randomize what the transport adds) + §4.2's size-bucket padding and fixed flush cadence. Transport: `iroh` if Rust, plain WebSocket otherwise — either way the hub dials out and the relay never dials in. Held to §4.3's `jeles-remote` bar: stateless, scales to zero, **the domain schema is absent rather than gated**, refuses to start without its keys.

**The edge replica** = Meadowcap-shaped area capabilities as the grant wire format, validated against Schedule A at issuance; one store per lane (CHT's database-per-user, not a filter); a cryptree-style key derivation so sibling sealing is a missing key rather than a missing `WHERE` clause; Evolu-class E2EE SQLite as the store if its per-Owner scoping checks out; PowerSync-style bucket-and-FIFO-queue semantics reimplemented rather than imported.

**Three acceptance tests that must be able to fail** (CLAUDE.md #19, and §14's note that no mutation gate exists for this app yet):

1. A session bound to mailbox A requests mailbox B's contents and is refused — and the refusal is structural, i.e. the request is unrepresentable, not rejected.
2. The relay is started with its keys removed and **fails to start** (the `jeles-remote` precedent, asserted rather than documented).
3. Two collection rounds against stores of different sizes produce identical response sizes; and separately, a test that asserts the leak that *survives* padding — weekly cadence — because `corpus-lens` already established that documenting the limit you measured is the artifact, and an audit note in prose is not an assertion.
